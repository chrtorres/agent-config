# Build and verify an interactive live-state app

Use this example when local events should drive a rendered interface. Activity Town reads session events through a loopback Node relay. A Three.js scene animates a figure between buildings and offers camera and cutaway controls. The browser receives a small classified activity object. The app labels synthetic activity and distinguishes it from a disconnected live feed.

## Reproduce the example

```sh
python3 -B <skill-directory>/scripts/create_app.py --example activity-town --destination <new-app-directory>
cd <new-app-directory>
npm ci
npx playwright install chromium
npm run smoke -- --evidence <fresh-evidence-directory-outside-the-app>
```

Use Node.js 20.19 or later, npm, and a Chromium browser with WebGL 2. Set `BROWSER_PATH` to select a browser executable explicitly. Browser dependencies and bundled fonts are acquired through the lockfile and Playwright installer. Geometry is generated by the included source.

Use the [example README](../assets/activity-town/README.md) for the preview and explicit live configuration. Live validation requires access to a compatible local session log. The smoke runner assigns separate temporary roots and generates its own synthetic sessions. A successful fixture run demonstrates browser behavior and the relay contract in isolation.

## Apply the workflow

1. Define the backend projection and its trust boundary before connecting the UI. Keep private input server-side. Give the frontend only the fields it needs to render and test the workflow.
2. Feed the same integration path with synthetic inputs. Exercise absent, stale, disconnected, and recovering states plus access from an unexpected origin. Keep evidence paths caller-selected and private.
3. Exercise actual movement and geometry. Wait for camera and scene observations published after rendering. On software renderers, control pixel load and allow bounded waits. Compare screenshots at matched camera positions and confirm that any image normalization still detects a deliberate geometry fault.
4. When the user requests independent local review, assign separate functional, privacy, and verification concerns. Review the intended revision, reproduce blockers locally, and recheck fixes on the revised candidate. Comment on non-obvious invariants and data boundaries using [comment-code](../../comment-code/SKILL.md). Record review decisions in the chosen evidence location.
5. Run smoke checks on the integrated revision when the delivery workflow includes a merge. Record local and hosted results independently when both are authorized. A browser job that times out on a shared runner needs diagnosis even when a workstation passes.

Historical user feedback, paraphrased. The user asked for local engineering reviews that could catch defects and for configuration values to stay out of published source. The team found tracking, session selection, and test false positives. The revised checks rejected deliberate camera and cutaway faults. On constrained runners, the suite also needed to wait for rendered state and account for subpixel raster differences. The user subsequently required code commenting as part of full-stack engineering. The skill now calls for the commenting pass, and the example explains session selection, privacy, and when the browser may trust rendered state.
