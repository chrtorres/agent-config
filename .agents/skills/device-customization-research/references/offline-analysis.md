# Offline acquisition and analysis

- Inspect installed tools and help first. Record versions/revisions. A Ghidra source checkout, Ghidra release installation, GhidraMCP extension, REA runtime and active MCP connection are distinct. Prefer the working integration instead of installing redundant services.
- Inspect REA's local requirements for Node/JDK/Ghidra and firmware engines. Do not run a setup command that writes agent configuration or installs skills as a side effect without relevant authorization. Use scoped environment paths; do not replace unrelated system runtimes unnecessarily.
- Obtain firmware only through the authorized source. Preserve URL, retrieval time, length, SHA-256, other declared digests and validation status. A public OTA is an offline candidate, not a live extraction. ZIP CRC/MD5 matches do not establish trusted vendor signing.
- Distinguish OTA, boot image, EFI capsule/FAT volume, filesystem, compressed payload and native ELF/PE components. Inspect metadata/container structure before choosing an extractor. Avoid executing extracted programs or update scripts. Preserve offsets, block-size assumptions, sparse/erase placeholders, decoded-child lineage and unsupported formats.
- Validate archive names and traversal before extracting; do not follow unknown links. Prefer read-only userspace filesystem inspection over mounting images or obtaining root merely to read them.
- Ghidra imports should preserve executable bytes, use a disposable project when suitable, and retain tool logs/limitations. Function names and counts are discovered inventory, not completeness. Missing functions may require justified code/function seeds; document the exact seed and analysis profile. Do not infer function semantics from names alone.
- Cross-check decompiler ABI/signature errors against headers, symbols, source mappings and instruction-level observations. Do not copy implementation output into a clean spec. A caller existing does not establish reachability or all-path effects.
- Keep firmware/kernel/userspace ABI distinct. Model/SoC identity, board routing, module vermagic/MODVERSIONS, graphics/HAL/Bionic dependencies and signing/boot policies matter independently. A compatible CPU family does not imply a compatible board image.
- Date-sensitive community compatibility and documentation must be verified at use time. Pin successful snapshots with provenance; retain failed retrievals and do not claim they were acquired.
